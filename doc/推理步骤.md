\## 0. 结论先行



1\. 这个模型不是一个 Transformer，而是 \*\*三段\*\*：global 12 层（帧间）+ local 1 层（帧内 17 步）

&#x20;  + 音频 decoder 12 层（code → 波形）。三段要分开优化。

2\. \*\*prefill 是算力受限，decode 是带宽受限\*\*。前者适合 GPU/NPU 批量 GEMM；后者是

&#x20;  batch=1 的 GEMV，权重每个 token 只读一次，\*\*谁的有效带宽高谁快\*\*——所以这版把 decode 放在 CPU。

3\. CPU decode 的唯一实质杠杆是\*\*减少每帧要搬的权重字节\*\*：fp16 → Q8\_0 → Q4\_0，

&#x20;  再把不敏感的张量降到 Q4、敏感张量保 Q8（混合精度）。内核直接移植 llama.cpp 的

&#x20;  `ggml\_gemv\_{q4\_0,q8\_0}\_4x4\_q8\_0`，量化块格式与 GGML 一致。

4\. 音频 decoder 本身是\*\*因果 + 有限滑窗注意力\*\*，patch 层只是 reshape，因此可以严格等价地

&#x20;  \*\*分块流式解码\*\*：LLM 每出 S 帧就解一块，边生成边出音频。首帧时延从 \~3 s 降到 \~0.43 s。

5\. 首帧时延 = `prefill + LLM 出首块 + 一步解码`；稳态速度 = `max(LLM 每帧成本, decoder 每帧成本)`。

&#x20;  两者要\*\*并行\*\*（不同线程/设备），并用「播放余量」而不是平均 RTF 做验收。

\## 1. 模型结构（先拆对，再谈优化）



| 模块 | 结构 | 频率 / 上下文 | 每帧计算量 |

|---|---|---|---|

| \*\*global transformer\*\* | GPT-2 12 层，d=768，12 头×64，MLP=3072，pre-LN，`gelu\_new`，interleaved RoPE | 12.5 fps | 12 层 × 1 步 |

| \*\*local transformer\*\* | GPT-2 \*\*1 层\*\*，同 768/12×64/3072 | 帧内 17 步 | 1 层 × \*\*17 步\*\* |

| \*\*输出头\*\* | text head 只取 2 行（slot=9 / end=7）；16 路 audio head = 输入 embedding（tied） | 每微步 | 16 × 1024×768 GEMV |

| \*\*量化前端\*\* | 16 码本 × LFQ(8 维) → 每本 1×1 conv 8→512，求和 → 512→768 | 每帧 | 很小，CPU |

| \*\*音频 decoder\*\* | 4 个 stage：4/2/2/4 层，d=256，4 头；patch 4/2/2/2/240；context 500/800/1200/1600 帧 | 50/100/200/400 Hz | 12 层注意力 |



关键常量：



\- \*\*一帧 = 80 ms = 3840 采样/声道 @48 kHz 立体声\*\*；码率 12.5 帧/s，每帧 16 个 code（0\~1023）。

\- 每帧 LLM 的层应用次数 = `global 12 + local 17 = 29`。

\- 单层参数 ≈ `c\_attn 768×2304 + c\_proj 768×768 + fc\_in 768×3072 + fc\_out 3072×768 ≈ 7.09 M`。

\- 每帧权重读取 ≈ `29 × 7.09 M + head 12.6 M ≈ 218 M` → fp16 \*\*436 MB/帧\*\*、Q8\_0 \*\*231 MB\*\*、Q4\_0 \*\*123 MB\*\*。

\- 上下文容量 `L + 生成帧数 ≤ 768`；prompt `L = 78(模板) + T\_ref(参考音频帧数) + n\_text`，

&#x20; 中文约 0.7\~0.8 token/字。长度上限按这个先算，不要等 OOM。



\### 1.1 prompt 的表示（克隆）



prompt 是 `\[L, 17]` 的整数矩阵，每行 = `\[text\_token, code0..code15]`：



```

\[im\_start, "user\\n", "<user\_inst>\\n- Reference(s):\\n", audio\_start]   # 头

&#x20; + T\_ref 行 \[audio\_user\_slot(8), 参考音频的 16 个 code]               # 参考音色

&#x20; + \[audio\_end, ...模板文本..., 待合成文本 tokens..., "</user\_inst>", im\_end,

&#x20;    "\\n", im\_start, "assistant\\n", audio\_start]                       # 指令 + 文本

\# 头 + 尾合计 78 个固定 token（L = 78 + T\_ref + n\_text）

```



embedding = `wte\[text\_id] + Σ\_{i<16} audio\_emb\[i]\[code\_i]`；`code=1024` 表示该通道无输入（pad，跳过）。

生成阶段每帧只喂一行：`\[wte\_slot(9), 上一帧的 16 个 code]`。

\## 2. 整体分几步



```

离线(一次)   文本 → TN → SentencePiece → ids ┐

&#x20;            参考音 → audio encoder → codes   ├→ prompt\_emb \[L,768]

&#x20;                                             ┘

在线每次请求

&#x20; ① prefill        prompt\_emb\[L,768] → 末位 hidden\[768] + 12 层 KV\[L,768]     ← 批量，算力受限

&#x20; ② 帧循环         每帧：global\_step → local 17 步 + 采样 → 16 个新 code        ← 单 token，带宽受限

&#x20; ③ 量化前端       16 codes → hidden\[768, T]                                    ← 很小

&#x20; ④ 分块解码       每 S 帧 → 波形 \[2, S\*3840]，与 ② 流水重叠                     ← 因果滑窗，可流式

```



| 步骤 | 设备建议 | 参考耗时（RK3588 单核） | 备注 |

|---|---|---|---|

| ① prefill L≈200 | GPU/NPU（批量 GEMM） | 200 ms | 每 token 复用一次权重 → 算力受限 |

| ② 帧循环 | \*\*CPU\*\*（或 GPU 常驻） | 26 ms/帧（混合精度） | 80 ms 预算 → 3× 余量 |

| ③ 量化前端 | CPU | < 1 ms/帧 | 查表 + 两个小 GEMM |

| ④ 解码 S=8 | NPU/GPU/CPU 均可 | \~270 ms/块（整步，含 I/O） | 与 ② 并行，不占关键路径 |

| 首帧总延迟 | — | \*\*\~430 ms\*\* | prefill 201 + 前 4 帧 72 + 首步解码 145 + 12 |



> 判断某一步该放哪：算 `ai = FLOPs / bytes`。prefill 的 `ai ≈ L`（几百），是算力受限；

> decode 的 `ai ≈ 1`，是纯带宽受限。`ai≈1` 的工作放到固定开销大、有效带宽低的加速器上通常更慢

> （这版实测 NPU 单步 decode 194 ms，CPU 10.3 ms）。

\## 3. 重点：LLM 的 CPU decode 是怎么做的



> 代码：`src/tts\_kernels.cpp`（GEMV）、`src/tts\_model.cpp`（block/local/global step）、

> `src/tts\_main.cpp`（帧循环/采样）。



\### 3.1 为什么 decode 放 CPU



单 token、batch=1 的 GEMV，每个权重元素只参与一次乘加，\*\*没有复用\*\*：

时间 ≈ 权重字节 / 有效带宽，而不是 FLOPs / 算力。RK3588 的 4×A76 实测冷读 \~13 GB/s、

热读 \~24 GB/s；218 M 权重/帧 → fp16 18\~34 ms，Q8\_0 10\~18 ms，Q4\_0 5\~10 ms。

优化方向只有两个：\*\*换更小的权重格式\*\*、\*\*让热数据留在 cache\*\*（local 层每帧读 17 次，天然热）。



\### 3.2 量化格式：直接对齐 llama.cpp / GGML



只借用 llama.cpp 的\*\*块格式 + GEMV 内核\*\*（冻结 commit `1623d8c`），没有用它的图调度/运行时（模型结构太特殊）。



| 格式 | 块布局（每 32 权重） | 字节/权重 | 说明 |

|---|---|---|---|

| fp16 | `\[32×fp16]` | 2.0 | 基线 |

| \*\*Q8\_0\*\* | `\[fp16 d]\[32×int8]` = 34 B | 1.0625 | 激活也按 32 一块动态量化成 Q8 |

| \*\*Q4\_0\*\* | `\[fp16 d]\[16×u8 两个 nibble]` = 18 B | 0.5625 | W4A8：权重 4 bit，激活仍是 Q8 |



\- 量化公式与 llama.cpp 一致：Q8\_0 `d = amax/127`；Q4\_0 `d = max\_signed/-8`，`q = round(w/d)+8`。

\- \*\*4×4 repack\*\*：把 4 个输出行交错成一组 `{fp16 d\[4]}{i8 qs\[128]}`（Q8）或 `{d\[4]}{u8 qs\[64]}`（Q4），

&#x20; 这样一次 NEON 点积能同时算 4 行，配合 `vdotq\_laneq\_s32`（A76 有 dotprod）把指令数压下来。

&#x20; 对应 llama.cpp 的 `ggml\_gemv\_q8\_0\_4x4\_q8\_0` / `ggml\_gemv\_q4\_0\_4x4\_q8\_0`（M=1 路径）。

\- 激活量化：每个 32 元素块取 absmax → int8，整数点积后乘 `s\_w × s\_x`，fp32 累加。

&#x20; \*\*LN / RoPE / softmax / residual 全程 fp32\*\*，只量化 4 个大矩阵和 head——这是数值能对齐的关键。

\- 移植到 x86：同样的块格式可用 AVX2/AVX-512 实现（`vpmaddubsw`/`vpmaddwd`），

&#x20; 或直接把这些矩阵交给 ggml 的 `ggml\_vec\_dot\_q4\_0\_q8\_0`；关键是\*\*保持块布局与 scale 语义一致\*\*。



内核骨架（Q4\_0 4×4，AArch64）：



```cpp

for (int c = 0; c < N; c += 4) {                 // 4 个输出行一组

&#x20; float32x4\_t acc = 0;

&#x20; for (int b = 0; b < K/32; b++) {

&#x20;   int8x16\_t b0..b3 = load(qs + 0/16/32/48);    // 4 行的 low nibble

&#x20;   int8x16\_t a0 = load(act\_q8 + b\*34 + 2);      // 激活 32×i8

&#x20;   int32x4\_t s = 0;

&#x20;   s = vdotq\_laneq\_s32(s, b0 << 4, a0, 0);      // 高 nibble

&#x20;   s = vdotq\_laneq\_s32(s, b1 << 4, a0, 1);

&#x20;   s = vdotq\_laneq\_s32(s, b2 << 4, a0, 2);

&#x20;   s = vdotq\_laneq\_s32(s, b3 << 4, a0, 3);

&#x20;   s = vdotq\_laneq\_s32(s, b0 \& 0xf0, a1, 0);    // 低 nibble

&#x20;   ...

&#x20;   acc = vfmaq\_f32(acc, vcvtq\_n\_f32\_s32(s, 4), vmulq\_f32(ad, bd));

&#x20; }

&#x20; store(out + c, acc + bias);

}

```



工程注意：



\- \*\*线程\*\*：只有 `N\*K` 足够大的矩阵才开 OpenMP（几万权重以下串行更快，省 fork/join）；

&#x20; 绑大核、按行连续切分；8 核全开常比 4 大核慢（小核拖累）。

\- \*\*不要每步分配\*\*：激活缓冲、KV、scratch 全部复用；LN 权重启动时转 fp32 常驻。

\- \*\*权重常驻\*\*：整份 CPU 权重只有 82.5 MB（混合精度），全部 mmap/常驻，别按请求加载。



\### 3.3 一个 token 的计算（global）



```cpp

block\_step(x, layer, kv\_k, kv\_v, pos):

&#x20; h  = x + c\_proj( attn( rope\_qk( c\_attn( LN1(x) ) ), kv, pos ) )

&#x20; y  = h + fc\_out( gelu\_new( fc\_in( LN2(h) ) ) )

```



\- KV cache：12 层 × `\[C,768]` fp32，K+V 合计 56.6 MB（C=768）。布局 `\[pos, 768]`，12 头×64 顺排，

&#x20; 写 K/V 时直接 `memcpy` 到 `pos` 行；attention 按 key 顺序扫（内存连续）。

\- RoPE 是 \*\*interleaved\*\*（相邻两维一组）：cos/sin 预计算成 `\[max\_pos, 768]` 表，

&#x20; 每步只查表，不调 `sincos`。

\- `gelu\_new` 用 tanh 的 Padé 有理近似，省 exp。

\- 12 层循环完再做一次 `g\_ln\_f`，得到这一帧的 hidden，作为 local 第 1 步的输入。



\### 3.4 local：每帧 17 个串行微步



原始实现每个微步都把「global hidden + 已生成的 token」整段重跑 local（长度 1→18），

因果注意力下与增量 KV \*\*数学等价\*\*（PC 验证 4.8e-6）。于是改成：



```

frame\_lc.reset()                                  // 帧内 KV \[18,768]，每帧清零

h = global\_hidden

local\_step(h) → text logits\[2] → 取 argmax 判 slot/end（end > slot 则整句结束）

xin = wte\[slot]

for ch in 0..15:

&#x20;   local\_step(xin) → hout

&#x20;   logits = audio\_emb\[ch] @ hout                 // 1024 logits，tied embedding

&#x20;   code\[ch] = sample(logits, temp=1.7, top\_k=25, top\_p=0.8)

&#x20;   xin = audio\_emb\[ch]\[code\[ch]]                 // 作为下一步输入

```



\- \*\*必须采样\*\*：audio 用 greedy 会退化成静音/循环；只有 text 的停止判决用 argmax

&#x20; （对齐参考实现 `do\_sample=False`，采样会让句子在随机帧被截断）。

\- 16 个 audio head 就是 `audio\_emb` 的 16 个 `\[1024,768]` 切片（tied），

&#x20; 所以 head 的 GEMV 可以复用 embedding 的量化副本——省一份 12 MB 权重。

\- local 每帧被读 17 次，是\*\*最热\*\*也是\*\*对量化最敏感\*\*的部分（17 步自回归会把误差反馈放大）。



\### 3.5 混合精度：怎么在「音质 ≈ Q8」下尽量少读字节



方法（可复用到任何自回归 TTS）：



1\. 用 \*\*teacher forcing\*\* 固定一批 Q8 生成的 codes，强制喂给所有候选，消除采样随机性；

2\. 每次只把一个 tensor 从 Q8 换成 Q4，比较 audio logits 相对 Q8 的 \*\*KL / top-25 重叠 /

&#x20;  参考 token 的 rank\*\*（不要用 MSE，采样看的是概率重排）；

3\. 每个 tensor 的性能收益用微基准或 `每帧访问次数 × 参数量 × Δbytes` 估；

4\. 按 `收益 / 敏感度` 从高到低放 Q4。



这版实测结论：local 的 4 个 tensor 敏感度是 global 的 4\~8 倍，所以——



| 部分 | 选择 |

|---|---|

| local `c\_attn` / `c\_proj` / `fc\_in` | \*\*Q8\_0 4×4\*\*（保） |

| local `fc\_out` | Q4\_0 |

| global `fc\_in`（×12） | \*\*Q8\_0 4×4\*\*（保） |

| global `c\_attn` / `c\_proj` / `fc\_out`（×36） | Q4\_0 |

| audio head（tied `audio\_emb`） | \*\*Q8\_0 4×4\*\* |

| `text\_head` / `wte\_slot` / LN | fp16（很小，别动） |



代价与收益（2 大核，75 帧 / 6 s，\*\*纯 CPU 帧循环，不含与 decoder 的争用\*\*）：



| 精度 | 帧循环 | ms/帧 | 相对 fp16 的 token 翻转 |

|---|---|---|---|

| fp16 | 2357 ms | 31.4 | — |

| 全 Q8\_0 | 1541 ms | 20.5 | 0 % |

| 全 Q4\_0 | 917 ms | 12.2 | 8.5 %（听感不可接受） |

| \*\*混合（上表）\*\* | \*\*1024 ms\*\* | \*\*13.7\*\* | \*\*1.5 %（听感≈Q8）\*\* |



> 单核时混合精度是 26.2 ms/帧，仍然只有 80 ms 预算的 33%；流式部署时与 decoder

> 并行争用，实测 20.4 ms/帧（2 核）。\*\*不要全 Q4\*\*——省下的 8 ms/帧换不来音质。

\## 4. 音频解码怎么变成流式的



> 代码：`src/tts\_npu.cpp`（`compute\_hidden` / `StreamAdec`）；设计推导：`docs/1009atdec\_streaming.md`、

> `docs/1020\_variable\_first\_chunk.md`。



\### 4.1 结构



```

codes\[16, T] → 量化前端(16×LFQ 8→512，求和，512→768) → hidden\[768,T]

&#x20; → patch4 → 4L Transformer @50Hz  (ctx 500)

&#x20; → patch2 → 2L @100Hz (ctx 800)

&#x20; → patch2 → 2L @200Hz (ctx 1200)

&#x20; → patch2 → 4L @400Hz (ctx 1600)

&#x20; → patch240 → reshape → 立体声 48 kHz（每帧 3840 采样/声道）

```



\### 4.2 为什么可以严格流式（三个条件，缺一不可）



1\. \*\*因果\*\*：第 t 帧的输出只依赖 ≤t 的输入；

2\. \*\*有限滑窗\*\*：每个 stage 的注意力只看最近 `context` 帧（500/800/1200/1600），

&#x20;  所以 KV 可以用\*\*环形缓冲\*\*，内存不随总长增长；

3\. \*\*patch 是纯 reshape\*\*：`patchN` 只做 `(B,C,T)→(B,C/N,N,T)` 的维度重排，

&#x20;  没有卷积/跨帧混合，因此按帧边界切块不产生接缝。



满足后，「分块解码 + KV cache」与「整段一次性解码」\*\*逐点等价\*\*（PC 验证 maxdiff \~3e-6）。



\### 4.3 两条落地路线



\*\*路线 A（推荐先做）\*\*：直接用原模型的 streaming 接口。

`MossAudioTokenizerModel.batch\_decode(..., chunk\_duration=...)` 内部就是

`MossAudioTokenizerDecodeSession` + `RingKVCache` + `\_forward\_streaming\_sdpa`，

已经处理了位置、mask 和 cache 回绕；先拿它做正确性基线，再决定要不要自己写。



\*\*路线 B（要极致性能时）\*\*：导出「step 模型」——每次吃 S 个新 code 帧：



```

输入 : hidden \[1,768,S]

&#x20;      bias\_s{0..3} \[1, S\*u\_s, C\_s + S\*u\_s]   // 加性 mask，0 / -1e4

&#x20;      k{0..11}, v{0..11} \[1, C\_s, 256]       // 3D，存未旋转的 K

输出 : audio \[1,2,S\*3840]

&#x20;      out\_k/out\_v ×12                        // 更新后的环形 cache

其中 u = {4,8,16,32}，C = {500,800,1200,1600}，层数 {4,2,2,4}

```



导成 ONNX / TensorRT / ggml 图都行；host 侧只维护 `pos\[4]`、`ck/cv\[12]` 和 mask 缓冲。



\### 4.4 两个通用数值坑（与平台无关）



1\. \*\*RoPE 位置精度\*\*：原实现用绝对位置 `base + arange(T)`。到 400 Hz stage、第 64 帧时

&#x20;  `base≈2048`，fp16 在 ≥2048 的整数分辨率是 2，连续帧的相位被量化 → 第 64\~69 帧误差尖峰。

&#x20;  \*\*解法\*\*：cache 存\*\*未旋转\*\*的 K，注意力时用\*\*相对位置\*\*（q: `0..T-1`，k: `-C..T-1`），

&#x20;  `|pos| ≤ C` 在 fp16 下整数精确。修复后整段 SNR 30.1 → 34.6 dB。

2\. \*\*mask 不要用 bool/动态构造\*\*：图内 `Greater/And/Where` 生成 mask 在部分后端会算错或

&#x20;  被折叠成巨大的 `S²` 常量。\*\*在 host 侧算好加性 float mask（0 / -1e4）喂进去\*\*，

&#x20;  图里只做 `Add`；bool mask 还可能因 `-inf` 溢出直接失真。



\### 4.5 调度：块大小 S、变长首块、不断流



一块 S 帧的音频时长是 `S×80 ms`，一步解码的耗时随 S 增大而增大（但摊到每帧更小）：



| S | 单步 | ms/帧 | 结论 |

|---|---|---|---|

| 1\~2 | \~190 ms | 92\~195 | 跟不上实时 |

| \*\*4\*\* | \~230 ms | \~57 | 实时下限；首帧最低 |

| 6 | \~223 ms | \~37 | 折中 |

| \*\*8\*\* | \~270 ms | \~34 | 推荐：总 RTF 与 LLM 持平 |

| 13 | \~340 ms | \~26 | 总耗时最低，但首帧变差、内存高 |



> 上表是 `fp32 I/O + 旧运行时` 的标定口径；换 fp16 cache/输出并减少每步 I/O 后，

> 首块 `S0=4` 可降到 \~145 ms，\*\*趋势不变\*\*：S 越小单步越快、每帧越慢。



\*\*变长首块（VFC）\*\*：首块用更小的 `S0`（如 4），之后切回 `S=8`，前 `N` 块用 `S0`。

收益是双份的——LLM 少等几帧、首步解码也更快。这版 `S=8 / S0=4 / N=2`

把首帧从 540 ms 降到 \*\*430 ms\*\*，音频 SNR \~50 dB、codes 逐位一致。



\*\*并行\*\*：decoder 放独立 worker 线程/队列，主线程每满 S 帧就快照 codes 入队；

decoder 只被 worker 串行访问（推理上下文通常非线程安全）。

稳态耗时 = `max(LLM 帧循环, decoder)`，首帧 = `prefill + S0 帧 LLM + 一步解码`。



\*\*验收用「播放余量」，不要只看平均 RTF\*\*：假设播放从首块就绪起 1× 实时消费，

第 k 块必须在「播放到该块起点」前就绪：



```

need\_by = first\_audio + 该块音频起点

margin  = need\_by - t\_ready        // < 0 就会断流

```



这版 `S0=2` 虽然首帧更低，但 `margin = -27 ms`，直接判死；`S0=4 N2` 的 `margin = +169 ms` 才上线。



\### 4.6 codes → hidden（量化前端）



原 decoder 输入对 codes 做 `Gather(axis=0)`；很多图编译器/加速器对这种数据相关索引不友好，

所以把它拆出来放 CPU：



```

hidden\[768,T] = output\_proj\_512→768( Σ\_{i<16} out\_proj\_i( codebook\_i\[code\_i] ) )

```



16 次「查 8 维表 → 1×1 conv 8→512」+ 一次 512→768。权重很小（\~2.3 MB），

按 `\[out, in]` 展开成两个 GEMM 即可，OpenMP 并行。这一步通常 <1 ms/帧，不值得上加速器。

\## 5. 从原始模型复现的推荐路线



\### 路线 A：有 GPU，先别做 CPU 技巧



模型只有 \~100 M 参数（fp16 210 MB），直接整份放 GPU：



\- prefill、decode、local、head 全部留在 GPU，用 fp16/bf16 + `torch.compile` 或手写融合 kernel；

\- decoder 用原模型的 `chunk\_duration` 流式接口，或导 step 模型到 TensorRT；

\- 单 token decode 是延迟受限，但 100 M 规模的 GEMV 在 GPU 上仍是毫秒级以内，

&#x20; 端到端 RTF 通常远小于 1。\*\*先跑通、再谈 CPU 卸载\*\*。



\### 路线 B：只有 CPU（或无 GPU 的端侧）



按这个顺序做，每步都有可验收的产物：



1\. \*\*基线对齐\*\*：PyTorch 固定 seed，dump 每帧 16 个 code 和 wav；

&#x20;  以后所有改动都要求 codes 逐位一致或 SNR > 45 dB。

2\. \*\*拆三段\*\*：global prefill（批量）、global decode（单 token）、local+heads（17 步）、

&#x20;  decoder（分块）。先全部用 fp16，确认数学等价（local 的增量 KV、decoder 的分块）。

3\. \*\*换 GEMV\*\*：把 4 个大矩阵和 16 个 head 换成 ggml/llama.cpp 的 Q8\_0 4×4 内核，

&#x20;  激活按 32 块动态量化；上 AArch64 用 `vdotq\_laneq\_s32`，x86 用 AVX2。

&#x20;  \*\*先在 PC 上做 packer 的 golden test\*\*（逐字节对比 llama.cpp 的量化/repack 结果）。

4\. \*\*混合精度\*\*：teacher forcing + KL 做逐 tensor 敏感度，按上表选型；不要全 Q4。

5\. \*\*流式解码\*\*：先用原模型 streaming API 验证分块等价，再决定是否导 step 模型；

&#x20;  块大小按「单步耗时 vs 每帧耗时」实测，首块用更小的 S0。

6\. \*\*并行 + 调度\*\*：decoder 独立线程，主线程只提交 codes；用 margin 检查不断流。

7\. \*\*调线程/绑核\*\*：只开大核；小矩阵串行；权重常驻；每步零分配。



\### 路线 C：GPU prefill + CPU decode（这版的形态）



prefill 用 GPU/NPU（`ai≈L`，算力受限），decode 用 CPU（`ai≈1`，带宽受限），

两者通过 24 个 KV 张量交接（`hidden\[768]` + 12×`K/V\[L,768]`，fp16 约 57 MB）。

注意 KV 要按 CPU 期望的 `\[pos,768]` 布局拷出，别在每帧做转置。

\## 6. 坑清单



| 坑 | 现象 | 处理 |

|---|---|---|

| 停止判决用采样 | 句子在随机帧被截断（固定 seed 时总在同一帧） | text 的 slot/end 用 \*\*argmax\*\*，只有 audio 采样 |

| audio 用 greedy | 静音/循环 | temp 1.7 + top\_k 25 + top\_p 0.8 |

| local 全量重算 | 17 步每步重跑 1..18 长度，慢且无必要 | 增量 KV（因果等价），每帧清零 |

| head 单独存一份 | 多 12 MB 权重 + 多一份量化 | head 与 `audio\_emb` tied，复用同一份 Q8 |

| 全 Q4 | logits 偏差 \~1.0，听感明显下降 | 只对 global 的 c\_attn/c\_proj/fc\_out 与 local fc\_out 用 Q4 |

| decoder 绝对位置 + fp16 | 64 帧后 SNR 掉到 30 dB | cache 存未旋转 K，用相对位置 |

| decoder 动态 bool mask | 某些后端失真/产生 S² 常量 | host 侧算加性 float mask |

| 首块用主模型 + padding | cache 里留下无效 key，后续全错 | 每步 `n` 必须等于该模型的 S；只有尾块允许 pad |

| 只优化平均 RTF | 平均很快但播放卡顿 | 逐块算 `margin`，`<0` 即不可上线 |

| prompt 超长 | L + 生成帧 > C，或 prefill 桶放不下 | 按标点分块；中文建议 ≤150 字/块 |
