# MOSS-TTS-Nano CPU 推理加速计划

> 目标：把 MOSS-TTS-Nano 的推理做成**能在大多数 Windows x64 电脑上直接跑的 CPU 版本**，精度以 **fp16** 为基准，速度尽可能快（瓶颈在内存带宽）。
> 三个阶段的产物都要可量化验收，不允许"感觉更快了"。

---

## 0. 一句话概述

| 阶段 | 做什么 | 验收 |
|---|---|---|
| 一 | LLM 段（global 12 层 + local 1 层）用 C++ 重写，**W8A8**（权重 Q8_0、激活 int8/32-block），fp16 路径作为同引擎内的对照基准 | greedy 模式下 codes 与 ONNX 基线一致；相对 fp16 路径的码一致率；ms/帧 |
| 二 | 逐张量把 Q8_0 换成 Q4_0，测**每部分的速度收益 / 精度损失**，选出最佳混合精度组合 | 一张消融表 + 一套定稿的量化方案 |
| 三 | 音频解码器（4 stage 因果滑窗）用 C++ 流式实现，fp16 基准 + W8A8 试验 | 与 ONNX 解码的 SNR；块级 margin（不断流） |

---

## 1. 约束与不变量

1. **精度基准 = fp16**。所有量化方案的"精度损失"都相对 fp16 路径测量，不相对 fp32。
2. **发布兼容性优先**：
   - 目标平台：Windows 10 1809+ / Windows 11，x64。
   - 主路径 **AVX2**（Haswell 2013 / Zen1 2017 起普及），**标量路径**作为兜底；**不要求 AVX-512**（Raptor Lake 已熔断，且服务器 CPU 才有）。
   - 可选 **AVX-VNNI**（Alder Lake+ P-core）走一条更快的 int8 内核，运行时检测，不作为必需。
   - 静态链接 CRT（`/MT`），**不用 OpenMP**（MSVC 的 `vcomp140.dll` 是额外依赖），线程用 `std::thread` 自建池。
   - 不依赖 GPU、不依赖 Python 运行时（Python 只在离线准备权重/对照时用）。
3. **线程上限 4**（用户指定）。默认绑 P-core；机器没有 P/E 区分时按物理核数取前 4 个。
4. **数值稳定优先**：LN / RoPE / softmax / residual / gelu 一律 fp32；只对 GEMM 做 int8。
5. 推理代码必须与 Python 侧解耦：C++ 只吃"token id 矩阵 + 权重文件"，不吃文本。

## 2. 现状基线（实测，2026-11-01）

ONNX CPU 路径（onnxruntime 1.31.1 CPU，4 线程，i5-14600KF）：

| 项 | 值 |
|---|---|
| 模型加载（8 个 session） | 6.0 s |
| 合成 5.36 s 音频（67 帧） | 2.26 ~ 2.32 s（热态） |
| 每帧 | 34 ~ 35 ms |
| RTF | 0.42 ~ 0.43 |
| 音频 | 48 kHz / 2ch |
| 确定性 | 固定 seed 两次逐位一致 |

> 冷启动首跑 6.8 s（670 MB `.data` 冷页缓存），对比耗时前必须热身。

### 2.1 算力/带宽账本

每帧的 LLM 层应用次数 = global 12 + local 17 = **29 次**，单层参数 ≈ 7.077 M：

| 精度 | 每帧权重读取 | 4 核查带宽 25 GB/s 的理论下限 |
|---|---|---|
| fp16 | 436 MB | ~17 ms |
| Q8_0 (1.0625 B/w) | 232 MB | ~9 ms |
| Q4_0 (0.5625 B/w) | 123 MB | ~5 ms |

**结论：这是带宽题，不是算力题。** 优化第一优先级是"每帧要搬多少字节"，第二是"让热数据留在 cache"。

## 3. 模型结构（精确到张量）

### 3.1 权重清单（`pytorch_model.bin`，194 个张量，bf16）

| 名称 | 形状 | 数量 | 备注 |
|---|---|---|---|
| `transformer.wte.weight` | 16384 × 768 | 1 | 文本 embedding |
| `transformer.h.{0..11}.*` | GPT-2 block | 12 × 12 | ln_1/ln_2、attn.c_attn(2304×768)、attn.c_proj(768×768)、mlp.fc_in(3072×768)、mlp.fc_out(768×3072) 及 bias |
| `transformer.ln_f.*` | 768 | 2 | global 末层 LN |
| `audio_embeddings.{0..15}.weight` | 1024 × 768 | 16 | 16 路码本输入 embedding |
| `text_lm_head.weight` | 16384 × 768 | 1 | 文本 head（实用上只用 2 行：slot=9 / end=7） |
| `audio_lm_heads.{0..15}.weight` | 1024 × 768 | 16 | 16 路音频 head |
| `local_transformer.h.0.*` | 同上 GPT-2 block | 12 | local 只有 1 层 |
| `local_transformer.ln_f.*` | 768 | 2 | local 末层 LN |

合计 ≈ **142.3 M 参数** → fp16 285 MB / Q8 151 MB / Q4 80 MB。

> 待确认：`text_lm_head` 与 `wte`、`audio_lm_heads` 与 `audio_embeddings` 是否数值相同（config 里 `tie_word_embeddings=true`，但 checkpoint 存了两份）。若相同，Q8 下可共用一份量化副本，省 25 MB 且减少一份带宽。

### 3.2 每帧前向（`_iter_generation_events` 的实际语义）

```text
每帧 step：
  ① global: inputs_embeds = wte[text_id] + Σ_i audio_emb[i][code_i]（code=1024 视为 pad，跳过）
             过 12 层（KV cache 复用）→ 取最后位置 hidden_768 → 转 local dtype
  ② local 第 0 位 = 该 hidden（单 token），过 1 层 + ln_f → text_lm_head → 采样 text token
     - 若 != slot(9) → 整句结束
  ③ 依次 ch = 0..15：
        local 输入追加一个 embedding（首次是 wte[text_token]，之后是 audio_emb[ch][code_ch]）
        过 1 层 local（**整段重算**，长度 1→18）→ 取最后位置 → audio_lm_heads[ch] → 采样 code
  ④ 下一帧 global 的输入行 = [9, code_0..code_15]
```

关键常量：

- 一帧 = 80 ms = 3840 采样/声道 @ 48 kHz 立体声；12.5 帧/s；每帧 16 码（0..1023）。
- 上下文上限 `L + 生成帧数 ≤ 768`；prompt `L = 78 + T_ref + n_text`。
- 采样：audio 用 temp 1.7 / top_k 25 / top_p 0.8 / repetition 1.2；text 只用 argmax 判 slot/end。
  > 注：ONNX 的 `sample_mode=fixed` 把这些超参烘进图里了。**我们的 C++ 自己实现采样**，所以必须与 ONNX 的 `fixed` 模式在相同输入下比 codes——greedy 模式最适合做严格对齐。

### 3.3 prompt 结构

`[L, 17]` 的整数矩阵（第 0 列是 text id，1..16 是 16 路 code）：

```text
[im_start, "user\n", "<user_inst>\n- Reference(s):\n", audio_start]
+ T_ref 行 [audio_user_slot(8), 参考音频的 16 个 code]      ← 音色
+ [audio_end, ...模板文本..., 待合成文本 tokens..., "</user_inst>", im_end,
   "\n", im_start, "assistant\n", audio_start]
```

阶段一由 Python 侧生成 prompt（SentencePiece 分词 + manifest 里的内置音色 codes），C++ 只读 id 矩阵。

## 4. 数值契约

### 4.1 量化格式（对齐 GGML，便于直接移植 llama.cpp 内核）

**Q8_0**（每 32 权重一组，34 B）：

```text
[ fp16 d ][ int8 q[32] ]        q = round(w / d), d = amax / 127
```

**Q4_0**（每 32 权重一组，18 B）：

```text
[ fp16 d ][ uint8 qs[16] ]      q = round(w / d) + 8, d = max_signed / -8
                                 qs[j] = q[2j] | (q[2j+1] << 4)
```

**激活**（W8A8 / W4A8 的 A8）：每个 32 元素块取 absmax → `d_a = amax/127` → int8；
累加用 int32，最后 `acc * (d_w * d_a)` 回 fp32；**LN/RoPE/softmax/residual 全程 fp32**。

### 4.2 精度验收（三级）

| 级别 | 对象 | 阈值 |
|---|---|---|
| L1 数值 | 单层 / 单步 logits vs PyTorch fp16（teacher forcing） | 相对误差 < 1e-2，无 NaN/Inf |
| L2 端到端 | greedy 模式下 67 帧 codes vs ONNX 基线 | **逐位一致**（fp16 路径）；Q8 允许 < 1% 翻转 |
| L3 听感 | 解码后音频 vs 基线音频 | SNR > 45 dB |

### 5.1 权重文件 `.moss`（单文件，便于分发）

```text
header:  magic "MOSW" | version u32 | n_tensors u32 | reserved
tensor table (n × 64B): name[48] | dtype u8 | ndim u8 | dims u32[3] | offset u64 | nbytes u64
data:    每个张量 32B 对齐（AVX2 load 需要）
```

`dtype`: `F16=0, Q8_0=1, Q4_0=2, F32=3`。同一份文件里不同张量可以是不同精度 —— **阶段二的消融就靠这个**，不用重编译。

### 5.2 量化方案描述文件（`quant_plan.json`）

```json
{
  "default": "q8_0",
  "overrides": [
    {"pattern": "global.h.*.attn.c_attn", "type": "q4_0"},
    {"pattern": "global.h.*.mlp.fc_out",  "type": "q4_0"}
  ]
}
```

`export_weights.py` 读它决定每张量的精度；C++ 只认权重文件里的 dtype。这样阶段二可以"一次导出多套", 也可以"一套文件 + 多份 plan"。

### 5.3 CLI 协议（阶段一）

```bash
moss_llm.exe --weights weights/q8.moss --prompt prompt.json \
             --frames 67 --threads 4 --greedy \
             --dump-codes out/codes.json --dump-logits out/logits.bin
```

`prompt.json`：`{"rows": [[text_id, c0..c15], ...], "seed": 0}`
`codes.json`：`{"frames": [[c0..c15], ...], "timings": {"prefill_ms": .., "per_frame_ms": [..]}}`

## 6. 阶段一：LLM W8A8

### 6.1 任务拆解

| ID | 任务 | 产出 | 验收 |
|---|---|---|---|
| T1 | `export_weights.py`：checkpoint → `.moss`（fp16 与 Q8_0 两套） | 权重文件 | 张量数量/形状/字节数自检；Q8 往返误差 < 0.4% |
| T2 | 标量内核（GEMV/GEMM + 量化 + LN + RoPE + softmax + gelu） | `gemv_scalar.cpp` | 单层对拍 PyTorch：rel < 1e-2 |
| T3 | AVX2 内核（Q8_0 4×4 GEMV、Q4_0 4×4 GEMV、激活量化） | `gemv_avx2.cpp` | 与标量内核逐元素对拍（int8 域完全一致） |
| T4 | KV cache + 因果 attention（fp32 K/V，`[pos,768]` 布局，interleaved RoPE 查表） | `llm.cpp` | 增量 decode 与整段 prefill 的 hidden 一致（< 1e-5） |
| T5 | local 1 层 + 17 步增量 KV（每帧清零） | 同上 | 与 PyTorch 逐帧 hidden 对拍 |
| T6 | 采样（temp/top-k/top-p/repetition，Xoshiro128++ 自实现，seed 可复现） | `sampler` | 同 seed 两次一致；greedy 与 ONNX 逐位一致 |
| T7 | CLI + 计时（per-phase + per-frame） | `moss_llm.exe` | 输出 JSON 可被 `compare_codes.py` 消费 |
| T8 | 对拍与调优 | 报告 | L1/L2 全绿；W8A8 相对 fp16 的码一致率 ≥ 99% |

### 6.2 性能目标（4 线程，67 帧，热态）

| 版本 | ms/帧 | 说明 |
|---|---|---|
| ONNX 基线（含解码） | 34 ~ 35 | 参照 |
| fp16 C++（仅 LLM） | ≤ 22 | 带宽下限 ~17 ms |
| **W8A8 C++（仅 LLM）** | **≤ 11** | 目标：接近 9 ms 的带宽下限 |

> 只统计 LLM 段（不含 codec 解码），否则无法与阶段二/三的收益区分。

### 6.3 关键实现要点

1. **GEMV 为主，GEMM 只在 prefill**：decode 是 M=1，用 4×4 repack 内核（一次算 4 个输出行，`vpmaddubsw` + `vpmaddwd`）。
2. **激活量化开销要摊薄**：一个 hidden 向量（768）只量化一次，被 12 层 × 4 个矩阵复用；local 的 17 步每步都要量化，注意缓存。
3. **注意力不计入瓶颈**：L ≤ 768、12 头，用 fp32 SDPA 标量实现即可；但要预计算 RoPE 的 cos/sin 表（`[768, 384]`），避免每步三角运算。
4. **零分配**：所有工作区在模型加载时一次性分配，帧循环里不 `new`/`malloc`。
5. **线程**：按输出行切分（`n_rows / 4`），用 `std::barrier`（C++20）或 spin barrier；4 线程绑 P-core（`SetThreadAffinityMask` 取物理核）。
6. **prefill**：M=L（78~300），走 8×4 分块 GEMM，激活一次量化、权重流式读；此时算力受限，int8 相对 fp16 有 ~2× 优势。

## 7. 阶段二：Q4 逐张量消融

### 7.1 方法

对每个候选张量组，只把它降到 Q4_0（其余保持 Q8_0），测三项：

1. **速度收益**：`Δms/帧`（同一次运行内，热态，4 线程，重复 5 次取中位）。
2. **精度损失**（teacher forcing 固定 Q8 生成的 codes，消除采样随机性）：
   - audio logits 相对 Q8 的 **KL**；
   - **top-25 重叠率**；
   - 参考 token 的 **rank 变化**；
   - 端到端 **code 翻转率**。
3. **单位收益**：`Δms / 精度损失`，按此排序。

候选组（按敏感度预期从低到高）：

| 组 | 张量 | 每帧读次数 | 预期 |
|---|---|---|---|
| G1 | global `attn.c_proj` | 12 | 最不敏感，先降 |
| G2 | global `attn.c_attn` | 12 | 低 |
| G3 | global `mlp.fc_out` | 12 | 低 |
| G4 | global `mlp.fc_in` | 12 | 中 |
| G5 | local 全部 | 17 | **高敏感**（17 步自回归误差放大） |
| G6 | `audio_lm_heads` | 16 GEMV/帧 | 高（直接决定 logits） |

### 7.2 产出

一张表（张量组 × 精度 → ms/帧、KL、翻转率、单位收益），据此定稿混合方案：

- 预期形态（待实测修正）：global 的 `c_attn/c_proj/fc_out` 用 Q4，`fc_in` 与 local 保 Q8，heads 保 Q8。
- 定稿写进 `quant_plan.json` 并纳入回归测试。

## 8. 阶段三：流式音频解码器

### 8.1 结构（`moss_audio_tokenizer`）

```text
codes[16, T] → 量化前端（16×LFQ 8→512 查表 + 1×1 conv，求和，512→768）
  → patch4 → 4 层 @50 Hz  (ctx 500)
  → patch2 → 2 层 @100 Hz (ctx 800)
  → patch2 → 2 层 @200 Hz (ctx 1200)
  → patch2 → 4 层 @400 Hz (ctx 1600)
  → patch240 → 立体声 48 kHz（每帧 3840 采样/声道）
```

三个可流式的条件：因果、有限滑窗（环形 KV）、patch 是纯 reshape。

### 8.2 任务

| ID | 任务 | 验收 |
|---|---|---|
| D1 | 从 ONNX 图/权重导出解码器参数（`.moss` 第二文件或同文件分区） | 张量齐全 |
| D2 | fp32/fp16 整段解码对拍 ONNX `decode_full` | SNR > 60 dB |
| D3 | 环形 KV + `step` 增量解码，S=8 分块 | 与整段逐点等价（maxdiff < 1e-4） |
| D4 | 流式管线：LLM 每满 S 帧 → 提交解码，计算块级 margin | margin > 0（不断流） |
| D5 | W8A8 试验（只量化 stage 内 4 个大矩阵） | 码不变 + SNR > 45 dB；速度收益记录 |
| D6 | 首块变长（S0=4）与调度 | 首帧延迟最优 |

> 解码器的量化收益预期低于 LLM（它的注意力占比更高、矩阵更小），所以放在最后，且**只有在 LLM 收益见顶后才值得做**。

## 9. 兼容性与发布形态

| 项 | 决定 |
|---|---|
| 编译 | MSVC 2022（14.44）+ CMake + Ninja；`/MT` 静态 CRT；`/utf-8` |
| 目标 | x64，`_WIN32_WINNT=0x0A00`（Win10 1809+） |
| CPU 分派 | 启动时 cpuid：`AVX2` → `gemv_avx2`；否则 `gemv_scalar`；可选 AVX-VNNI 内核 |
| 依赖 | 无第三方库；不依赖 VC++ 运行库、不依赖 OpenMP DLL |
| 体积 | 单 exe < 1 MB；权重 Q8 ≈ 151 MB（阶段二混合后 ≈ 120 MB） |
| 内存 | 权重常驻 + KV 60 MB + 工作区 < 16 MB；峰值目标 < 400 MB |
| 分发 | `moss_llm.exe`（CLI）+ 权重文件；后续插件用 DLL 导出 C API |

> 明确的取舍：**不做 AVX-512 优化、不做 ARM64 NEON**（标量路径保证能跑，不保证快）。

## 10. 度量方法学（避免自欺）

1. 每次测量前跑 **3 帧热身**（权重进 cache、线程池唤醒）。
2. 每个配置跑 **5 次**，报中位数与最小值；抖动 > 10% 要查原因（后台进程、降频）。
3. 只统计 **LLM 帧循环**（`per_frame_ms`），不含模型加载与文件 IO。
4. 线程数固定 4，绑核策略固定（P-core 0-3 逻辑）；测量时关闭其它重负载。
5. 精度实验一律 **teacher forcing**（固定 codes），否则采样随机性会淹没差异。
6. 端到端 RTF 只在阶段三结束后报，且要报块级 margin。

## 11. 风险与回退

| 风险 | 影响 | 回退 |
|---|---|---|
| int8 激活量化引入的误差在 17 步自回归里放大 | 音质下降 | local 段保持 fp16 权重/激活（只量化 global） |
| AVX2 GEMV 达不到带宽下限（4 线程不够） | 速度不达标 | 优先减少字节（Q4 消融）、增大块内并行、prefetch |

## 附录 D：阶段二首轮消融（2026-11-01）

### D.1 方法

- **teacher forcing**：三个权重版本喂**完全相同**的 f16 codes（24 帧），只比较每步预测与 logits。
- 度量：`KL(f16 || 候选)`（温度 1.7，与采样分布一致）、top-25 重叠、top-1 一致率、code 翻转率。
- 工具：`--dump-logits` + `tools/compare_logits.py`。

### D.2 结果（4 线程，prompt 196 行）

| 精度 | 权重体积 | ms/帧 | 相对 f16 | KL | top-25 重叠 | top-1 | code 翻转 |
|---|---|---|---|---|---|---|---|
| f16 | 224 MB | 10.72 | 1.00× | 0 | 100% | 100% | 0% |
| **Q8_0（全部矩阵）** | 119 MB | **6.96** | **1.54×** | **0.0009** | **97.4%** | 94.0% | 6.0% |
| Q4_0（全部矩阵） | 63 MB | 6.61 | 1.62× | 0.361 | 59.7% | 29.4% | 70.6% |

### D.3 结论

1. **Q8 是明确的赢**：快 1.54×，KL 仅 0.0009，top-25 重叠 97.4%。
2. **全 Q4 在当前内核下没有价值**：只比 Q8 快 5%，精度却崩了（翻转 70%）。
   原因不在精度，在**内核**——Q4 每帧只搬 123 MB 却只跑到 18.6 GB/s（Q8 是 33 GB/s），
   说明 Q4 路径被 nibble 解包 + 每块 `hsum` 拖成**算力受限**，带宽优势完全没吃到。
3. **下一步必须先优化内核，再谈 Q4**：
   - 4×4 repack（4 行共享激活载入与 scale 转换，每 4 块只做一次水平求和）；
   - 激活按 Q4 通道预拆成 even/odd int16，避免每行重复 shuffle。
   目标：Q8 到 40 GB/s（≈5.8 ms/帧），Q4 到 30 GB/s（≈4.1 ms/帧）。
4. 在 repack 之前，**混合精度的收益评估没有意义**：Q4 的"每张量收益"目前全是噪声。

### D.4 本轮的其它改动

- prefill 改为**按层批量 GEMM**（权重只读一遍）：659 → 253 ms，与逐行结果 **384/384 逐位一致**。
- 量化矩阵的块 scale 在加载时展开成 fp32 表，内核里不再做 fp16→fp32 软件转换。
- `--threads N` 线程池（std::barrier，无 OpenMP 依赖），4 线程实测。

### G.1 权重与张量命名（`model-00001-of-00001.safetensors`，374 个张量，83.8 MB）

| 组 | 张量数 | 说明 |
|---|---|---|

### G.2 解码链路（`decoder_kwargs` 展开）

```text
codes[16, T]（12.5 fps）
  → quantizer.decode_codes：16 路 LFQ 各取 codebook 行（8 维）→ out_proj → 求和 → [768, T]
  → patch4（768 → 192 通道，T × 4）
  → ProjectedTransformer：4 层，d=256，4 头，ff=1024，RoPE，LayerNorm，layer_scale=0.01，causal，ctx 10 s
  → patch2（768 → 384，T × 2）→ 2 层 transformer → 3 层同理
  → 最后一层 transformer 输出 240 通道 → patch240 → 波形（每帧 240 采样/声道）
```

Patch 的语义（`MossAudioTokenizerPatchedPretransform.decode`，L1941）：

```python
x: [b, d*h, l] → reshape(b, d, h, l) → permute(0,1,3,2) → [b, d, l*h]
```

即"通道拆成 h 份、时间维乘 h"，**纯 reshape，无跨帧混合** → 可严格按帧边界切流式。

### G.3 实现要点（下一轮照此写）

1. 布局：`conv_layout: True` → 内部张量是 `[B, C, T]`（通道优先），与 LLM 的 `[T, C]` 相反，C++ 侧统一成 `[C][T]` 连续。
2. 每层结构：`x += layer_scale * attn(LN(x))`，`x += layer_scale * mlp(LN(x))`，`layer_scale` 是**可学习标量**（每层一个）。
3. 注意力：环形 KV（ctx 帧），RoPE 用**相对位置**（文档 4.4 的坑），mask 在 host 侧算好加性 float。
4. 流式块大小 S=8（首块 S0=4），每块输出 `S×240×2` 采样；验收用块级 margin 而不是平均 RTF。
5. 精度基准：先 fp32 整段对拍 ONNX `decode_full`（目标 SNR > 60 dB），再切流式（对拍 maxdiff < 1e-4），最后才试 W8A8。

### H.2 语义验证（关键）

`tools/decoder_reference.py` 用 torch 复刻整条解码链，与 ONNX `decode_full` 对拍（同一份 67 帧 codes）：

### H.3 确认的实现细节（C++ 照此写）

1. **codes 布局**：ONNX 用 `[B, T, nq]`，内部计算用 `[nq, T]`。注意别搞反。
2. **量化前端**：`z = Σ_i (codebook_i[code_i] @ out_w_i^T + out_b_i)` → [512, T]；再 `output_proj`(768×512) → [768, T]。
3. **patch**：`[C,T] → [C/p, T*p]`，纯 reshape：`reshape(d, p, t).permute(0,2,1).reshape(d, t*p)`。
4. **每层**：`x += ls1 * attn(LN1(x))`，`x += ls2 * ffn(LN2(x))`；`ls` 是**每通道**向量 [256]，不是标量；FFN 无 bias，GELU 是**精确版**（erf，不是 tanh 近似）。
5. **注意力**：`in_proj`(768×256) 无 bias，输出按 `[T,3,H,D]` 切 q/k/v；RoPE interleaved、绝对位置、`max_period=10000`；因果 mask。
6. **窗口**：`context = round(frame_rate × context_duration)`，解码侧最短是 10 s@100 Hz = 1000 帧，远大于我们 T*32 ≈ 2144 中的短句场景，**短句可先忽略窗口**，但流式实现必须保留。
7. **立体声**：末级 patch240 输出 `[1, T*7680]`，按奇偶**去交织**成 2 声道（每帧 3840/声道）。

## 附录 J：解码器精度/性能实验（2026-11-01，D5 初测）

### J.1 权重精度对比（67 帧，4 线程，同 codes）

| 权重格式 | 体积 | 解码耗时 | vs ONNX fp16 的 SNR |
|---|---|---|---|
| fp32 | 43.7 MB | 536.9 ms | **52.59 dB** |
| **fp16** | **22.3 MB** | 533.8 ms | **52.03 dB** |
| Q8_0 | 12.2 MB | 514.8 ms | 25.88 dB |

**结论：解码器用 fp16**。Q8 只省 4% 时间却损失 27 dB——音频波形对权重误差远比 LLM 的离散 codes 敏感；
而 fp16 几乎无损（-0.56 dB）且体积减半。

### J.2 性能剖析（关键发现）

- 权重从 fp32 换 q8（体积 1/3.6）只快 4% → **解码器不是权重带宽瓶颈**。
- 分阶段耗时（fp16）：stage1 21 ms / stage2 26 ms / stage3 64 ms / **stage4 418 ms**。
- stage4 在 T=2144 上做 4 层因果注意力，估算 FLOPs ≈ 4.7 GMAC（注意力）+ 5.9 GMAC（GEMM），
  实测 ~400 ms → 约 13~25 GMAC/s，**注意力实现效率不足**（每点积一次水平求和的标量链）。
- 已做的优化（AVX2 内积 + 每线程 scores 缓冲）只带来 6%，说明还差在**分块与数据复用**。

### J.3 下一轮要做的

1. **注意力分块**：查询按 64 一块、键按块复用，消除 T² 规模的重复载入；目标 stage4 降到 120 ms 以内。
2. **流式（D3/D4）**：真正收益不是减少 FLOPs（因果注意力本身就只算过去），而是
   **把解码与 LLM 生成重叠、首块提前出音**；环形 KV 把内存从 O(T) 固定为 O(ctx)。
3. 全链路目标：LLM 616 + 解码 ~300 → 约 0.9 s（ONNX 基线 2260 ms，约 2.5×）。

## 附录 K：流式解码（D3/D4 完成，2026-11-01）

### K.1 实现

- 每段独立**环形窗口 KV**（500/800/1200/1600 帧，对应 context_duration × 该段帧率），
  注意力只看 `delta < context` 的键；超出窗口的旧键 memmove 掉。
- 块内 patch 自洽（S 帧 → 4S/8S/16S/32S 位置，全部整除），块间靠 KV 衔接，无需保留 patch 余数。
- CLI：`moss_decoder --stream S`。

### K.2 正确性

| 对比 | 结果 |
|---|---|
| 流式（S=8，9 块）vs 整段解码 | **maxdiff 2.37e-6**（相对 2.7e-6） |
| 整段（带窗口）vs ONNX fp16 | **61.14 dB** |
| 流式 vs ONNX fp16 | **61.13 dB** |

> 顺带发现：**整段解码必须也带窗口**。之前忽略窗口时对 ONNX 只有 52 dB；补上窗口后升到 61.1 dB，
> 说明 ONNX 的 `decode_full` 同样按 `context_duration` 截断。

### K.3 延迟/吞吐（67 帧 / 5.36 s，fp16 权重，4 线程）

| 块大小 S | 首块延迟 | 总耗时 | 解码 RTF |
|---|---|---|---|
| 4 | **20.9 ms** | 623.5 ms | 0.116 |
| **8（推荐）** | 39.0 ms | **598.0 ms** | **0.112** |
| 16 | 89.2 ms | 602.8 ms | 0.113 |

首块延迟 = 解码 S 帧的时间；S=4 时 **21 ms 就能出 320 ms 音频**，完全满足流式起播。

### K.4 全链路（可流水线）

| 段 | 耗时 | 每帧 |
|---|---|---|
| LLM（Q8_0_4x4） | 616 ms | 6.4 ms |
| 解码器（fp16，流式 S=8） | 598 ms | **8.9 ms** |
| 串行合计 | ≈ 1215 ms | — |
| **流水线后（取两者较大 + 启动）** | **≈ 750 ms** | — |

解码器现在是**更慢的一段**（8.9 vs 6.4 ms/帧）。若要让 LLM 等解码，需要继续优化解码器的注意力
（当前是逐点积 + 水平求和，没有分块复用）。

## 附录 L：全链路集成 + 兼容性（2026-11-01）

### L.1 `moss_tts.exe`（LLM + 解码器单进程）

```
moss_tts --llm weights/llm_q8x4.moss --decoder weights/decoder_f16.moss \
         --prompt runs/cpp/prompt.txt --frames 67 --chunk 8 --threads 4 \
         --out out.wav [--dump-codes codes.txt]
```

- LLM 逐帧生成 → 攒满 S 帧 → 解码器 `decode_chunk` → 追加 PCM；最后写 48 kHz 立体声 WAV。
- 与已验证的流式解码输出对拍：**SNR 74.83 dB**（差异只是 int16 量化），峰值 0.8892 一致。
- codes 与 `moss_llm` 逐位一致（1072/1072）。

### L.2 实测（67 帧 / 5.36 s 音频，4 线程）

| 阶段 | 耗时 |
|---|---|
| 权重加载（LLM+解码器） | 67.6 ms |
| prefill（196 行） | 178.4 ms |
| 生成 + 解码（串行） | 1023.6 ms（内含解码 577.4 ms） |
| **首音延迟** | **263.5 ms** |
| **总墙钟** | **1271 ms** |
| RTF | **0.237** |

ONNX 基线同句 2260 ms → **约 1.8 倍速（串行）**；若把 LLM 与解码器做成双线程流水线，
预计墙钟 ≈ 178 + 40 + 577 ≈ **800 ms（约 2.8 倍速）**。

> 注意：目前两个模型共用同一个全局线程池 `parallel()`，**不能**同时从两个线程调用；
> 要实现真流水线，需要把 `Parallel` 改成按模型实例持有（下一轮的工作）。

### L.3 兼容性检查（发布前提）

`dumpbin /dependents build\moss_tts.exe`：

```
KERNEL32.dll
```

只有系统 DLL。**没有** `vcruntime140.dll` / `msvcp140.dll` / `vcomp140.dll` / `libomp.dll`
——静态 CRT + 不用 OpenMP 的目标已达成。

### L.4 一个踩过的坑

`moss_tts` 最初把攒下的 codes 按 **帧主序** 交给解码器，而 `decode_chunk` 期望 **nq 主序**
（`codes[i*T + t]`）。症状不是崩溃，而是音频完全不对（对拍 -4 dB）。已在 `flush_chunk` 里转置。

## 附录 M：运行时降级验证（2026-11-01）

用 `MOSS_FORCE_SCALAR=1` 强制走标量路径（模拟没有 AVX2 的老机器），两个引擎都跑通：

### M.1 解码器

| 路径 | 解码耗时 | 与 AVX2 输出 |
|---|---|---|
| AVX2 | 501 ms | — |
| **标量** | **773 ms**（1.54×） | maxdiff 2.4e-6、**SNR 120.5 dB** |

标量与 AVX2 数值等价（只是浮点累加顺序不同），速度可接受。

### M.2 LLM

| 路径 | prefill | ms/帧 | codes 与 AVX2 |
|---|---|---|---|
| AVX2（Q8_0_4x4） | 176 ms | 6.39 | — |
| **标量** | 175 ms | **16.75**（2.6×） | 12.87% 相同 |

LLM 的 codes 差异大是**预期**的：int8 点积的累加顺序不同 → logits 差 ~1e-6 → argmax 翻转 →
上一步 code 反哺下一步 → 级联（和"Q8 vs f16 只有 6% 一致"是同一现象）。音频听感等价，但不是逐位一致。

> 结论：**降级路径可用**。发布时不需要 AVX2 也能出声，只是慢 1.5~2.6 倍、且与 AVX2 机器上的
> 具体波形不完全相同（这在 8bit 量化 + argmax 采样下无法避免，除非降级路径使用 fp16 权重）。

### M.3 一个观察

LLM 的 prefill 在标量路径下**没有变慢**（175 vs 176 ms）。说明 prefill 的耗时不在 GEMM 上
（可能被注意力/归一化的开销主导），这是后续优化 prefill 的一个线索。

## 附录 N：泛化验收 + 流水线尝试（2026-11-01）

### N.1 跨文本/跨音色验收（teacher forcing，对 ONNX greedy codes）

| 用例 | 音色 | prompt 行数 | token 翻转率 |
|---|---|---|---|
| 基准句（中文） | Junhao | 196 | 6.5% |
| 中文长句（含数字） | Junhao | 199 | **12.5%** |
| 英文 | Ava | 192 | **19.9%** |
| 中文（女声） | Xiaoyu | 273 | **14.8%** |

三个新用例都在 10~20% 区间，与基准句同量级，**没有出现"某个文本整体错乱"的情况**。
说明 tokenizer、prompt 模板、音色 codes、长句分块这几条路径都是通的。

> 为什么不是 0%：teacher forcing 下 int8 logits 与 ONNX fp16 的差已经足以翻转部分 argmax，
> 这是量化 + 离散采样的固有性质，不是实现错误（fp16 路径对 ONNX 也有 27.9% 翻转）。

### N.2 流水线尝试：失败并回退

想把 LLM 与解码器放两个线程重叠（预期 1276 → ~850 ms），做法是把线程池从全局单例改成
`thread_local`，让两个线程各持一份。

**结果：`--pipeline 1` 在 `threads >= 2` 时死锁**（`--threads 1` 正常）。
现象是进程不输出、不退出，`strace` 级别的定位受限于工具，未能根因定论；
最可疑的是 `std::barrier` 在多线程池场景下的使用方式（每个池的参与者计数与 worker 唤醒顺序）。

**处置**：删掉线程化分支，`moss_tts` 只保留顺序模式（1276 ms / RTF 0.238）。
流水线不是目标的一部分，但它是"再快一点"的最直接手段，记在这里供以后重做
（正确做法：把 `Parallel` 改成显式实例 + 由调用方传递，而不是靠 thread_local 隐式取）。
