# MOSS-TTS CPU v0.1.1

修掉 v0.1.0 里"音频播到一半开始卡、没播完就结束、末尾一截听不到"的播放缺陷，
并加上"边播边算"（限速生成）选项。

## 修复：播放端丢音频

v0.1.0 的主线程把收到的 PCM 一块接一块直接 `postMessage` 给音频线程。推理约 7 倍实时，
一段 9.3 s 的语音 1.2 s 就算完了，音频线程 4 s 的环形缓冲被灌满，**多出来的部分直接丢弃**。

用真实的 `pcm-worklet.js` + 真实的 HTTP 流做无浏览器重放，问题可复现：

| 逻辑 | 实际播放 | 丢样 |
|---|---|---|
| v0.1.0（来一块推一块） | 5.19 s / 9.28 s | **4.09 s** |
| v0.1.1（信用窗口） | 9.28 s / 9.28 s | 0 |

现在主线程最多领先播放位置 2.5 s，缓冲满了就不读 socket（HTTP 背压会让服务端也慢下来），
另加"流结束把不足 128 帧的尾巴也播完"。回归脚本 `tools/playback_sim.mjs`
逐样点比对输出与输入，已并入发布门禁。

## 新增：边播边算（`pace`）

网页上多了一个勾选项，默认开启：

> 只比播放位置快 1.5 秒生成，CPU 平时只忙 15% 左右，风扇不会突然狂转。
> 关掉则一次算完（适合短句或急着要文件）。

接口层是 `POST /api/v1/tts/stream` 的新字段 `pace`（秒，0 = 不限速，默认 0）。
`GET /api/v1/jobs/{id}` 新增 `wall_ms`（墙钟）；`compute_ms` 现在**只算模型真正干活的时间**，
限速等待和阻塞发送都被扣掉，所以 RTF 仍然是模型速度，不会被限速算法污染。

实测（16 帧 = 1.28 s 音频，`pace=1.0`）：墙钟 0.53 s，compute 0.27 s。
取消在限速模式下仍然 30 ms 内响应。

## 同版本内的其他变化

- 页面上显示"墙钟"和"丢样/欠载"计数，异常时一眼能看出来。
- 发布门禁多了两步：`pace` 实测、播放重放（`tools/playback_sim.mjs`）。
