# 并行推理 · 音色克隆 · 独立发版

> 承接 `doc/推理加速计划.md`（阶段一~三：LLM W8A8、Q4 消融、流式解码器、全链路 CLI）。
> 本文覆盖第四阶段：把 LLM 与解码器并行起来、把「音色克隆」做成 C++ 能力、把推理端做成可独立分发的产品。

## 0. 两个先搞清楚的事实

### 0.1 克隆不是「一个向量」，是 N 帧音频码

上游（`vendor/moss_tts_nano_onnx/ort_cpu_runtime.py:build_voice_clone_request_rows`）的 prompt 结构：

```
[12 个 user_prompt_prefix_token_ids] + [audio_start]      ← 文本行（code 槽填 audio_pad=1024）
[N 帧 [audio_user_slot=8, code0..code15]]                 ← 参考音频（克隆）
[audio_end] + [58 个 after_reference] + [正文 token] + [6 个 assistant_prefix] + [audio_start]
```

- 参考音频由 `moss_audio_tokenizer_encode.onnx` 编码：输入 `(1,2,T)` 48 kHz 立体声，**每 3840 个单声道样本一帧（80 ms）**，16 路 × 1024 码本。
- 内置音色的参考长度 32~218 帧；`data/clone_wav` 三个样本（44.1 kHz 立体声 float32）是 **72 / 136 / 126 帧**，编码耗时 286/713/586 ms（ONNX，4 线程）。
- **前 `72 + N` 行只和音色有关**，与文本无关 → 这段 prefill 可以算一次、存 KV、以后直接加载。

### 0.2 结束判定：不是「帧数到了」，是一次概率抽样

上游 `_sample_assistant_text_token` 把候选**限制在两个 token** 上（`audio_assistant_slot=9`、`audio_end=7`），
再按 softmax 概率抽一个。所以「说完了」是每帧一次伯努利试验：

- 抽到 9 → 继续出帧；抽到 7 → 结束。
- 只要某一帧 `p(end)` 有几个百分点，长句里就几乎必然提前结束 —— 这正是「token 长度有概率提前结束」的成因。

**实测（本机，Q8_0_4x4 权重）**：

| 场景 | 逐帧 `logit[9] - logit[7]` 轨迹 | 结果 |
|---|---|---|
| 贪心出音频（`--greedy`） | 400 帧全程 **+10 ~ +14**，从不下穿 0 | 模型永远不主动结束，只能靠帧数上限 |
| 采样出音频（manifest 默认 0.8/25/0.95/1.2） | 末段 **12.2 → 11.9 → 9.3 → 6.9 → 3.8 → 2.5 → 0.59 → -0.50** | 第 64 帧干净收尾（5.12 s） |
| 上游 full 路径（Python 侧抽样） | 最后一次决策 **+0.61** | 第 89 帧结束（7.1 s） |

结论：
1. 模型确实有一条**斜坡式**的结束信号（末 5~6 帧从 12 掉到 0），不是突变；
2. 上游那种「按概率抽」在斜坡中段的任意一帧都可能抽到 end（margin=3 时 p≈5%/帧）→ 早停；
3. **改成贪心（`logit[7] > logit[9]` 才停）既保留了自然收尾，又不会随机截断**；配合 `--min-frames` 安全阀。
4. 贪心出音频时永远不会结束（信号不收敛），所以**默认走采样出音频**、贪心只用于对拍 —— 两条正好互补。

顺带解释了基线里的 67 帧：那是 ONNX 图内抽样在 67 帧处抽到了 end（不是帧数上限），我们采样版是 64 帧，同一量级。

## 2. 设计要点

### 2.1 线程模型：每个引擎一个池，谁用谁持有

上一轮失败的根因是「全局 `thread_local` 线程池 + 引擎内部直接 `parallel()`」：池和调用方没有一一对应关系，
`std::barrier` 的参与者计数一旦错配就挂死。现在：

- `Parallel` 是普通对象，`LlmModel`、`AudioDecoder`（后续 `AudioEncoder`）**各自持有一个**；
- 删除 `init_parallel()` / `parallel()` 全局入口；`gemv_par` / `gemm_par` 通过 `GemvPoolScratch::bind(Parallel&, k)` 拿到自己的池；
- `Parallel::run` 里加**重入/并发降级**：同一个池被重入或两个线程同时用时，退化为串行执行并置 `degraded`，绝不进 barrier 等死；
- 流水线：LLM 在生产者线程，主线程当消费者，中间是**有界帧队列**（容量 4×chunk，满了阻塞生产者 = 背压）。

### 2.2 前缀 KV 缓存（待实现）

- `LlmModel::prefill(rows, start_pos)`：RoPE 位置从 `start_pos` 起算，KV 写到 `[start_pos, start_pos+m)`，注意力看 `start_pos+i+1` 个 key。
- 不可变前缀 = `12 + 1 + N + 1 + 58` 行；每段文本开头把前缀 KV memcpy 回工作区（72 KB/位置，N=136 时约 15 MB / ~3 ms）。
- `.mosspfx`：`magic|ver|layers|n_pos|hidden|prefix_fingerprint|weights_fingerprint|f32 kv[layers][2][n_pos][hidden]`，
  指纹不符直接拒绝加载（避免换了权重还吃旧缓存）。

### 2.3 编码器（待实现）

解码器的镜像，权重全是 Linear（无 bias）+ LayerNorm + layer_scale + interleaved RoPE：

```
(1,2,T) 交织 → 补零到 7680 的倍数
patch240 → PT(240→384, 4L, 窗1600) → patch2 → PT(768→384, 2L, 窗1200)
patch2  → PT(768→384, 2L, 窗800)  → patch2 → PT(768→192, 4L, 窗500) → patch4
→ 768 → in_proj 512 → 16×[LFQ: 512→8 → L2 归一 → 最近邻(1024×8) → out_proj 8→512 → 残差]
```

窗口数 = `context_duration ÷ 该段帧间隔`，与解码器的 {500,800,1200,1600} 正好反序。

## 3. 阶段 A 实测（2026-11-01，i5-14600KF）

产物：`runs/pipeline/{p0,p1}_greedy.wav`、`sample_pipe.wav`、`*_gate.csv`。

### 3.1 重构没有改变数值

| 检查 | 结果 |
|---|---|
| 重构前后同一命令的 WAV | SHA256 **相同**（`a1_serial.wav` == `final2.wav`） |
| codes | 完全相同 |
| pipeline 0 vs 1 | WAV 与 codes 都**逐位相同** |
| 线程数 1/2/4/8 | 同一 seed 都出 **64 帧**、codes 相同（并行只切行，求和顺序不变） |

### 3.2 并行收益（67 帧 / 5.36 s，chunk 8，贪心）

| 配置 | prefill | 解码合计 | 首音 | wall（含加载） | RTF |
|---|---|---|---|---|---|
| 串行 `--pipeline 0` | 179.4 | 644.4 | 268.3 | 1353.4 | 0.2525 |
| 并行 4+4 | 172.5 | 664.8 | 265.9 | **1037.1** | 0.1935 |
| 并行 4+6 | — | 527.9 | 261.2 | **955.7** | 0.178 |
| 并行 4+8 | — | 526.2 | 267.1 | 950.4 | 0.177 |
| 并行 2+6 | — | 537.5 | 418.0 | 1189.1 | 0.222 |
| 并行 6+4 | — | 659.4 | 230.6 | 1014.5 | 0.189 |

- 解码器在 6 线程饱和（526 ms ≈ 7.9 ms/帧），再加线程无收益 → 瓶颈是**每段一次 barrier 的调度开销**，不是算力（见阶段 E）。
- LLM 降到 2 线程时 prefill 明显变慢（首音 418 ms），所以 LLM 侧不要低于 4 线程。
- chunk 扫描（4+6）：chunk 4 → 首音 222 ms / 合计 966 ms；chunk 8 → 265 ms / 970 ms；chunk 16 → 363 ms / 1038 ms。

### 3.3 采样 + 自然结束（产品路径）

`--sample --seed 0 --threads 4 --decode-threads 6 --chunk 8`：

```
frames 64（5.12 s）  first_audio 262.7 ms  wall 956.0 ms  RTF 0.1867
```

对比阶段三定稿的串行 1276 ms / RTF 0.238 → **1.33×**，且这是「模型自己收尾」的完整一句话。

### 3.4 稳定性

- 同一命令连跑 10 次：64 帧 ×10，wall 896.6 / 917.3(中位) / 951.0 ms，无挂起。
- 线程极端组合 1+1、2+2、2+4、8+8 全部正常结束（旧实现 1+1 之外必挂）。
- `--dump-gate` 留下的 CSV 可复现 0.2 节的余量轨迹。

## 4. 阶段 B：前缀 KV 缓存（完成）

`LlmModel::prefill(rows, start)` 支持接着已有 KV 往后写；`snapshot_prefix / restore_prefix` 在内存里留一份
「音色那一段」的 KV；`save_prefix / load_prefix` 落盘成 `.mosskv`（magic + 12 层 × K/V + rows 指纹 + 权重指纹）。

实测（196 行 prompt = 170 行音色前缀 + 26 行正文，67 帧，chunk 8，4+6 线程）：

| 场景 | prefix | suffix | prefill 合计 | 首音 | wall | RTF |
|---|---|---|---|---|---|---|
| 不切前缀 | — | — | 175.4 | 263.8 | 932.5 | 0.178 |
| 切前缀（缓存 miss） | 158.3 | 26.2 | 184.5 | — | 934.0 | — |
| 切前缀（缓存 **hit**） | **4.6** | 29.4 | **34.0** | **123.9** | **776.3** | **0.152** |

- 缓存文件 11.95 MB（170 个位置 × 12 层 × 2 × 768 × 4B），加载 4.6 ms。
- **三条路径的 codes 与 WAV 逐位相同**（SHA256 相等）：不切 / 切（miss）/ 切（hit）→ 缓存不影响数值。
- 指纹不符（换权重、换 prompt）→ stderr 提示并自动重算，不会静默吃错缓存。
- prefill 从 175 → 34 ms，首音从 264 → 124 ms；这是**每句话**都省，长文本分块时每块都省。

## 5. 阶段 C：C++ 编码器与音色克隆（完成）

### 5.1 实现

- `tools/export_encoder.py` → `weights/encoder_f16.moss`（21.8 MB，210 个张量）/ `encoder_f32.moss`（42.4 MB）。
- `AudioLayer`（layernorm / interleaved RoPE / GELU / 一层前向）从解码器抽出来共用；
  解码器改用它之后输出**逐位不变**（`runs/pipeline/dec_{before,after}.f32` SHA256 相同）。
- `AudioEncoder`：patch240 → 4 段（窗口 1600/1200/800/500，与解码器反序）→ patch4 → 768→512 →
  16 路残差 LFQ。`moss_clone.exe`：WAV → 重采样 48 kHz → 编码 → `.mossclone`（几 KB，可分享）。

### 5.2 与 ONNX 编码器对拍（三个克隆素材）

| 素材 | 时长 | 帧数（我们/ONNX） | 编码耗时 | codes 一致率 |
|---|---|---|---|---|
| deepseek_letmogo | 6.3 s | 79 / 79 | 640 ms | **97.7%** |
| ranran_first | 10.7 s | 134 / 134 | 1282 ms | **93.9%** |
| taffy | 9.9 s | 124 / 124 | 1115 ms | **91.6%** |

- 帧数完全一致；阶段耗时 477/99/35/25/2 ms（stage1 占 75%，符合「序列最长、注意力最贵」）。
- f32 权重的一致率与 f16 **相同**（97.5/93.3/91.6%）→ 剩余差异不是权重量化，而是图内的混合精度
  （导出图里有大量 Cast，部分算子走半精度）。
- **回放验证（这才是硬指标）**：把我们和 ONNX 的 codes 分别过解码器，
  对原始音频 SNR **6.03 dB vs 6.01 dB** —— 16 路 VQ 往返本来就只有 ~6 dB，两者等价。
- **对 LLM 的影响**：用两套 codes 各建一个克隆 prompt，teacher-forced 翻转率 **5.99%**，
  与量化本底 6.0% 同量级 → 两个 prompt 在模型眼里是同一个音色。

### 5.3 这里踩的两个坑

1. **LFQ 的最近邻在归一化空间，但重建残差必须用原始码本向量**。
   `decode_latents` 里 `codebook = F.normalize(codebook)` 只用于算距离，随后 `decode_code_wo_out_proj`
   用的是**原始** `codebook.weight`。我一开始两边都用了归一化码本 → codes 与 ONNX 只有 7% 相同
   （回放峰值 1.9、严重削波）。改正后 92~98%。定位方法：把 ONNX 图里 `/encoder.*/output_proj`、
   `/quantizer/input_proj` 的中间张量加成输出（`tools/onnx_add_outputs.py`），逐段对拍。
2. **`data/clone_wav/*.wav` 其实是 MP3-in-WAV**（`fmt` tag = 0x55 / 0x1B0，`block_align=1`、`bits=0`）。
   `moss_clone` 只吃 PCM WAV，测试前先用 torchaudio 转成 PCM。发版文档要写清这一点。

- `scripts/pack_release.bat [zip]` 一键组装 `dist/moss-tts-cpu-win64`。

### 6.4 这一阶段踩的坑

1. **Windows 下 `main(int, char**)` 收不到 UTF-8**：命令行是 UTF-16，C 运行时会转成 ANSI(GBK)，
   中文 `--text` 被打碎 → 每个字节都落到 byte-fallback（52 字节 → 52 个 token，模型立刻结束）。
   改用 `wmain` + `WideCharToMultiByte(CP_UTF8)` 解决。
2. **`.mossclone` 是 10 个字符**，我按 11 判后缀，导致 `--profile x.mossclone` 被当成音色名。
3. `voice_.codes` 是 `int16_t`，`build_voice_prefix` 却按 `int32_t*` 读 → prompt 全是垃圾码，
   模型第一帧就判结束（frames=0）。改成 `int16_t*`。
4. cmd 里 `copy "src" "dst\"` 的结尾 `\"` 会被当成转义引号；`.bat` 还必须纯 ASCII（一行中文注释就能拆错命令）。
   打包脚本因此改成 `scripts/pack_release.bat` + 全 ASCII 注释 + 目标路径不带结尾反斜杠。
5. 每路音色的前缀 KV 缓存 12~18 MB（落在 `models/cache/*.mosskv`），18 个内置音色全用会占 ~250 MB；
   删掉即可重建，属于派生数据。

## 8. 阶段 E：流式注意力（完成，并修掉一个真 bug）

### 8.1 做了什么

原来的流式注意力是 `run_layer_stream` 里一段逐 query 的标量循环（每层每 worker 一份 scores 缓冲）。
现在抽成 `attention_window()`（AVX2 + 标量两份实现，运行时 cpuid 分派）：

- 键集合 = 「缓存（cache_n 个）+ 当前块」，有效区间解析成一个连续下标区间
  `[max(0, i+cache_n-window+1), i+cache_n]`，省掉逐键的 `delta` 判断；
- 内积走 4 路展开的 `_mm256_fmadd_ps`，softmax 与加权求和也向量化；
- 接口按「查询区间 [q0,q1)」切分，和 `attention_causal` 一致。

### 8.2 顺手抓到的真 bug（重要）

第一版把「worker 切片的 qkv 指针」当成了整块的起点传进去，导致**键的读地址整体偏移了 i0**：
块越大偏移越多。表现是分块解码和整段解码对不上：

| 对比 | 修之前 | 修之后 |
|---|---|---|
| 流式（chunk 8）vs 整段 | 第 0 块 **0.85**，后面每块 ~0.0014 | **0.0（逐位相同）** |

这个 bug 在旧实现里也存在（我用 `-DOLD_STREAM_ATTN` 把旧代码编出来做过 A/B，输出一模一样），
所以之前文档里「流式 vs 整段 2.4e-6」的说法只在特定配置下成立。现在**分块解码与整段解码逐位一致**，
分块边界不再有任何数值差。

### 8.3 实测

| 项 | 数值 |
|---|---|
| 整段解码（67 帧） | 531 ms（7.9 ms/帧） |
| 流式 chunk 8 | **414 ms（6.2 ms/帧）**，首块 35 ms |
| 流式 vs 整段 | **maxdiff 0.0** |
| 整段 vs ONNX | **61.14 dB**（未变） |
| 端到端 5.12 s（Junhao，热缓存） | 首音 128 ms / 764 ms / **RTF 0.149** |
| 端到端 13.0 s（Xiaoyu，冷缓存） | 首音 400 ms / 2320 ms / **RTF 0.178** |

注意：**AVX2 注意力本身没有提速**（改前改后流式都在 380~414 ms）。chunk=8 时每层注意力只有 8 个查询，
真正的开销是每层几次 `par.run` 的 barrier + GEMM。所以「解码器慢」的锅不在注意力，而在
**层内小批次调度**；要再快得合并 barrier（例如把 LN/RoPE/残差合成一次 `run`），这是后续可选项。
