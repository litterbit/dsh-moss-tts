# MOSS-TTS CPU 引擎：产品化与分发方案（评审稿）

> 日期：2026-11-04
> 状态：待评审。本文是**现状 + 目标 + 初步计划**的完整陈述，供外部评审使用。
> 读者不需要访问本仓库即可理解全部内容；所有关键数字都来自本机实测。

**摘要（TL;DR）**

- **方案**：GitHub Pages 上放一个纯静态页；页面上的按钮从 GitHub Release 下载一个 Windows 程序（含 160 MB 权重，解压即用）；程序常驻在 `127.0.0.1:8759`，网页用 `fetch` 连它，流式拿 PCM 边下边播。推理 100% 在用户本机，与未来 DSH 插件共用同一个 exe。
- **为什么不 WASM**：WASM 要把 2 个 AVX2 内核重写成 SIMD128，速度掉一半以上，而且无法与插件共用一份二进制。代价是用户必须下载一次。
- **关键可行性**：`http://127.0.0.1` 在 https 页面里被浏览器豁免混合内容阻断；但 Chrome 104+ 的 Private Network Access 预检必须在服务端实现（`Access-Control-Allow-Private-Network: true`），且不能用 WebSocket。
- **工作量**：P0 协议验证 0.5 h → 服务端 1 天 → 网页 1 天 → 仓库外化/CI 0.5 天 → 首个 Release 0.5 天，合计约 3 天。
- **最大风险**：SmartScreen 拦截（未签名）、GitHub Pages 国内可达性、Chrome PNA 政策收紧。
- **需要评审拍板**：架构选型、分发形态（full/lite/安装器）、安全模型（要不要 token）、以及第 7 节的 12 个开放问题。

## 0. 给评审者的话

**一句话背景**：这是一个纯 C++ 的 MOSS-TTS-Nano-100M CPU 推理引擎（Windows x64，零第三方运行时依赖），已经跑通、量化定档、性能调优完成。现在要把它变成"任何人打开一个网址、下载一个程序、就能在自己的电脑上实时合成语音"的产品，并且这套推理**未来必须原样成为 DeepSeek Harness（DSH）的一个 TTS 插件**，不能为网页和插件各写一套推理。

**请你重点审的问题**：

1. 架构选型（远端静态页 + 本地伴生进程）是否有更优雅的替代？WASM / 云端 / 桌面壳（Tauri/Electron）的取舍我判断得对吗？
2. 浏览器到 `127.0.0.1` 这条链路（混合内容豁免 + Private Network Access 预检 + 无 WebSocket）是否有我漏掉的坑？有没有更稳的跨浏览器做法？
3. 分发方式（GitHub Release full/lite 双包 + HuggingFace 权重仓 + 可选 Inno Setup 安装器 + `mosstts://` 协议唤起）是否过度设计或设计不足？160 MB 的下载体验有没有更好的做法？
4. 安全模型（只绑 127.0.0.1 + Origin 白名单 + 不用 token）是否足够？有没有 CSRF / DNS rebinding 类风险我低估了？
5. 计划里的阶段划分、估时、验收标准是否合理？有没有该提前做的技术验证？
6. 第 7 节列了 12 个开放问题，请逐条给意见，能直接给方案更好。

**本方案的前提假设**（如果某条不成立，方案要改）：

- A1. 目标用户以 Windows 10/11 x64 为主，愿意为"本地推理"下载一次 ~160 MB 的程序。
- A2. 首次运行有 SmartScreen 警告是可接受的（不买代码签名证书）。
- A3. 不做账号、不做云端推理、不改模型权重。
- A4. 网页由 GitHub Pages 托管，仓库公开。
- A5. 音频必须**流式**播放（首包 100 ms 级），不是"等整段生成完再播"。

### 1.3 实测性能（i5-14600KF，6P+8E，AVX2，无 AVX-512）

单句 5.12 s 中文、64 帧、4+6 线程（打包后实测）：

| 指标 | 数值 |
|---|---|
| 首音延迟 | 75~128 ms（首块 4 帧策略，实测波动来自缓存冷热） |
| 总耗时 | 764 ms |
| **RTF** | **0.149** |
| LLM prefill | 167~176 ms（181 行 prompt，约 0.9 ms/行） |
| LLM decode | 7.39 ms/帧（W8A16） / 6.43 ms/帧（W8A8） |
| 解码器 | 5.9~6.2 ms/帧（流式 chunk 8，环形 KV） |
| 内存 RSS | ~249 MB |

线程数实测（同一句，ms/帧）：4+4 = 6.88，3+3 = 7.65，2+2 = 11.35，1+1 = LLM 12.5 / 解码 19.4（首音 202 ms，RTF 0.337）。建议按物理核数给：2 核→2+2，4 核→3+3，6 核以上→4+4（解码器可给到 6）。

进程启动 + 加载权重实测 **67 ms**，跑 8 帧的整进程耗时 **190 ms**（其中合成 102 ms）。这是"每句话起一个进程"的固定开销。

### 1.4 精度边界（已做过完整实验，不需要再讨论）

| 配置 | code 翻转率 | KL | 备注 |
|---|---|---|---|
| f16 参考 | 0 | 0 | 上限 |
| Q8 权重 + A16 decode（**发布默认**） | 5.2% | 0.00145 | 听感与参考无差异 |
| Q8 + A8（旧配置） | 8.7% | 0.0042 | 备选 |
| Q4 任何组合 | 64~86% | 0.44~1.16 | **不可用**，音频响度暴涨 5 倍并削顶 |

结论：8 bit 是这台模型的底线；再往下只能换量化方案或优化解码器。这条已经封板，本方案不改精度。

### 1.6 现有的"网页"只是开发用的试听台

## 2. 目标

### 2.1 用户故事

**U1（非技术用户）**：看到一条网址 → 打开 → 页面上点「下载」→ 得到一个 zip（或安装器）→ 解压双击 → 回到页面 → 输入文字 → 听到声音。全程不看命令行、不知道"模型文件"是什么、不需要管理员权限。

**U2（开发者）**：`pip` 之外的任何语言都能用——CLI 一行合成、或 `POST http://127.0.0.1:8759/api/say` 拿流式 PCM。

**U3（插件用户）**：装了 DSH 的 TTS 插件，插件里选音色、调语速/温度，对话时直接出声。**插件与网页用的是同一个 exe、同一份权重、同一套参数语义。**

### 2.2 硬性要求

| # | 要求 | 验收方式 |
|---|---|---|
| R1 | 一条固定网址，任何人可打开 | GitHub Pages URL 公开可访问 |
| R2 | 页面内一次点击即可下载可运行的程序 | 下载 → 双击 → 浏览器里能出声，全程 ≤ 3 步 |
| R3 | 推理在用户本机 CPU 完成，不上传文本/音频 | 断网后仍可用（下载完成后） |
| R4 | 流式播放，首包 ≤ 300 ms | 页面显示的首音指标；主观上"打字即出声" |
| R5 | 与未来插件共用同一套推理实现 | 同一 exe / 同一 C ABI，插件不引入第二份推理代码 |
| R6 | 不需要管理员权限、不写系统目录 | 便携目录或 `%LOCALAPPDATA%` |
| R7 | 弱机可用 | 4 核机器 RTF < 0.5；线程数可自动推荐 |
| R8 | 可离线 | 下载后拔网线仍能合成 |

### 2.3 明确不做（本轮）

- ❌ 云端推理服务（违背"用自己的电脑算"，且 CPU 云主机成本不可接受）
- ❌ 账号 / 计费 / 用量统计 / 遥测
- ❌ macОS / Linux 版（核心代码可移植，但不是第一版的事）
- ❌ 移动端（iOS/Android 浏览器连不上本机服务）
- ❌ 训练 / 微调
- ❌ 第一版就上 WASM（见 3.2）

### 2.4 验收标准（可测）

1. 一台干净的 Win11（无 VS、无 Python、无 VC++ redist）：下载 zip → 解压 → 双击 → 30 秒内听到第一句。
2. 页面在 Chrome / Edge / Firefox 最新版上都能连上本地引擎；Safari 走"打开本地页面"兜底。
3. 连续合成 20 句不崩、不泄漏内存（RSS 稳定在 250±30 MB）。
4. 同一文本 + 同一 seed，网页与 CLI 产物 SHA256 相同。
5. 关掉引擎后，页面 2 秒内把状态切回"未检测到引擎"，并给出恢复引导。
6. `curl http://127.0.0.1:8759/api/ping` 返回版本与线程信息。

## 3. 方案

### 3.1 总体架构

```
                       ┌────────────────────────── GitHub ──────────────────────────┐
                       │ 仓库（源码 0.6 MB）  Actions（构建/回归/打包）  Pages（静态页）│
                       │                      Release（full zip / lite zip / sha256）│
                       └───────────┬──────────────────────────────┬─────────────────┘
                                   │ ①打开页面                     │ ②点下载（普通跳转）
                                   ▼                              ▼
                        ┌────────────────────┐          ┌──────────────────────┐
                        │  静态网页（遥控器） │          │ 用户本机：解压/安装   │
                        │  无模型、无算力     │          │ moss_tts.exe --serve │
                        └─────────┬──────────┘          └──────────┬───────────┘
                                  │ ③fetch http://127.0.0.1:8759    │
                                  │   （CORS + PNA 预检）           │ 加载权重一次
                                  └────────────────────────────────►│ 推理，吐 PCM
                                                                    │
   DSH 插件（Node）──spawn──► moss_tts.exe --pcm-raw -  ──stdout──► 同一份引擎二进制
```

三层分离，接口只有两个：

- **C ABI**（`moss/tts.h`）：进程内调用，插件/第三方程序链接静态库时用。
- **HTTP 协议**（本地 127.0.0.1）：进程外调用，浏览器与任何语言用。

网页和插件都只是"这两个接口的客户端"，**推理实现只有一份**。

### 3.2 为什么不是 WASM / 云端 / 桌面壳

| 方案 | 速度 | 需要重写的代码 | 与插件同一套 | 结论 |
|---|---|---|---|---|
| **A. 远端静态页 + 本地进程**（本方案） | 1:1 原生（RTF 0.15） | HTTP 服务 ~400 行 | ✅ 同一 exe | **采用** |
| B. 浏览器内 WASM | 估 RTF 0.4~0.5（SIMD128 无 VNNI，int8 点积要模拟） | 重写 2 个 AVX2 内核 + pthreads + emscripten 工具链，3~5 天 | ❌ 第二套产物 | 延后，非必需 |
| C. 云端推理 | 看网络 | 服务端整套 + 付费 | ❌ 与"本机算"矛盾 | 排除 |
| D. Tauri/Electron 桌面壳 | 1:1 原生 | 打包层 | ⚠️ 多一个运行时 | 可作为 A 的补充壳，非必需 |

补充：WASM 若要做多线程需要 `SharedArrayBuffer`，必须带 `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` 响应头，**GitHub Pages 不支持自定义响应头**，得换 Cloudflare Pages / Netlify / HF Space。也就是说 B 方案连托管都要换，而 A 方案用 Pages 完全够。

### 3.3 浏览器侧可行性（已查证的三条规则）

**规则 1：混合内容豁免。** https 页面默认禁止请求 http 资源，但 `http://127.0.0.1` / `http://localhost` 被视为"潜在可信来源"而豁免（Chrome 79+、Edge 79+、Firefox 84+）。参考：[MDN · Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Mixed_content#loading_locally_delivered_mixed-resources)。**Safari 不支持**，需兜底"打开本地页面"。

**规则 2：Private Network Access 预检。** Chrome 104+ 在公网页面访问本机前会先发 `OPTIONS` 预检，请求头带 `Access-Control-Request-Private-Network: true`，**服务端必须在预检响应里回 `Access-Control-Allow-Private-Network: true`**，否则被拦。参考：[Chrome for Developers · PNA preflights](https://developer.chrome.com/blog/private-network-access-preflight)。这是唯一"不实现就静默失败"的点。

**规则 3：不能用 WebSocket。** `ws://` 没有 loopback 豁免，会被判为混合内容拦掉。因此协议走 **HTTP/1.1 chunked 流式响应**，前端用 `fetch` + `response.body.getReader()` 逐块喂 WebAudio。

结论：A 方案在主流 Chromium/Firefox 上可行；预检头必须实现；协议不要用 WS。

### 3.4 页面：一份 HTML，两种打开方式

同一份 `web/index.html` 既部署在 GitHub Pages，也被本地服务在同一路径托管。API 基址自适应：

```js
const isLocal = ['127.0.0.1', 'localhost'].includes(location.hostname);
const API = isLocal ? '' : 'http://127.0.0.1:8759';
```

页面加载时并行探测 `GET /api/ping`（端口依次试 8759…8763，每个超时 300 ms），落进三种状态：

| 状态 | 判定 | 页面元素 |
|---|---|---|
| **未安装** | 所有端口无响应，且 `localStorage.mossInstalled` 为空 | 「下载本地引擎（159 MB）」大按钮 + 三步图文 + SmartScreen 提示截图 |
| **已安装未运行** | 无响应但曾成功过 | 「启动本地引擎」按钮 → 跳 `mosstts://start`；1.5 s 无响应则提示"双击桌面图标 / start.bat" |
| **运行中** | `/api/ping` 成功 | 正常合成界面；右上角绿点显示 `v0.1.0 · 4+6 线程 · RTF 0.15` |

页面功能清单：文本框（Ctrl+Enter 合成）、音色下拉（内置 + 克隆）、克隆上传（拖 wav）、温度/top-p 两个滑杆、种子、流式播放 + 暂停/续播、下载 WAV、生成历史（内存保留最近 8 条）、错误提示人话化（不出现 `Failed to fetch`）。

### 3.5 本地服务协议（草案）

只监听 `127.0.0.1`（不弹防火墙、外网不可达）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ping` | `{version, engine:{llm, decoder, tokenizer}, threads:{llm, decode}, voices:n, ready:bool, rtf_hint}` |
| GET | `/api/voices` | `{builtin:[...], clones:[{name, seconds}]}` |
| POST | `/api/clone` | body = 原始 WAV 字节，`?name=xxx`；返回 `{name, frames, seconds}`；写入 `models/voices/` |
| POST | `/api/say` | body JSON `{text, voice|profile, seed, greedy, max_frames, temp, top_k, top_p, rep}`；**响应 `Content-Type: audio/L16;rate=48000;channels=2`，`Transfer-Encoding: chunked`，body 为 s16le 交织 PCM 流** |
| POST | `/api/say?format=wav` | 同上但返回带 RIFF 头的完整 WAV（用于下载，不能用 `<audio>` 流式播） |
| GET | `/`、`/assets/*` | 静态文件（`web/` 目录） |

预检响应必须包含：

```
Access-Control-Allow-Origin: <命中白名单时回显 Origin>
Vary: Origin
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: content-type
Access-Control-Allow-Private-Network: true
Access-Control-Max-Age: 86400
```

白名单来自 `web/origins.txt`（可配置、免重编译）：`https://<user>.github.io`、`http://127.0.0.1:*`、`http://localhost:*`。非白名单 Origin 一律 403。

上层规则：

- **不用 token**：白名单已足够（跨站读取拿不到响应；跨站 POST 会被预检挡住）。代价是 curl/本地脚本可直连——本机范围内的风险可接受。
- **取消**：客户端断开连接（`send()` 返回 WSAECONNRESET）即停止生成、释放本次请求。
- **并发**：引擎单实例，请求进队列串行处理；第二个标签页会排队而非抢占 CPU。
- **错误**：`4xx/5xx` 返回 `{"error": "中文可读信息", "code": "..."}`。
- **统计回传**：chunked 响应结束后无法带 trailer 给 `fetch`，页面侧自行计时；详细统计只在 `/api/ping` 与日志里。**（此处希望听到更好的做法，见 Q4）**

### 3.6 进程与入口设计

**单 exe 多入口**：`moss_tts.exe`

| 调用 | 行为 |
|---|---|
| 无参数 | 起服务（默认端口 8759）+ 自动打开默认浏览器 |
| `--serve [--port N] [--no-open]` | 显式起服务 |
| `--text "..." --out a.wav` | CLI 合成（现有） |
| `--pcm-raw -` | 流式 PCM 到 stdout（现有，插件用） |
| `--selftest` / `--list-voices` / `--version` | 现有 + 新增版本号 |

理由：发布包里少一个二进制、用户不会点错；`WS2_32.dll` 链接进同一 exe 的代价可忽略（仍然是纯静态 CRT）。
反方意见（希望评审）：HTTP 服务代码混进 CLI 主程序是否影响可维护性？拆成 `mossd.exe` 是否更好？

### 3.7 权重与分发

三层，各司其职：

| 层 | 载体 | 内容 | 理由 |
|---|---|---|---|
| 源码 | GitHub 仓库（公开） | 0.6 MB 代码 + 文档 | Pages 免费版要求公开仓库 |
| 权重真身 | **HuggingFace 模型仓** | `llm_q8x4.moss` / `decoder_f16.moss` / `encoder_f16.moss` / `tokenizer.mossvocab` / `voices/*` / `manifest.json` | 支持 Range 断点续传、按 revision 钉版本、浏览器可跨域 fetch（未来 WASM/在线下载需要）。**GitHub Release 资产不保证 CORS**（见 [community#45446](https://github.com/orgs/community/discussions/45446)） |
| 开箱包 | GitHub Release | `moss-tts-v0.1.0-win64-full.zip`（159 MB，含权重）、`-lite.zip`（~3 MB，不含权重）、`sha256sums.txt` | Release 单文件上限 2 GB，普通 `<a>` 跳转下载不需要 CORS，网页上点一下就下 |

`manifest.json`（放在 HF 仓与仓库里各一份，内容一致）：

```json
{
  "version": "v0.1.0",
  "files": [
    {"path": "llm_q8x4.moss", "bytes": 125047648, "sha256": "..."},
    {"path": "decoder_f16.moss", "bytes": 23350368, "sha256": "..."}
  ]
}
```

**下载逻辑放在"外壳"里，C++ 核心永不联网**：full zip 自带权重；lite 包由 Node 插件/浏览器 `fetch` 下载（两者都有原生 fetch）。这样核心二进制不需要 TLS 客户端（不背 schannel/OpenSSL），依赖依然干净。

**为什么不全放 Release**：每次发版复制 160 MB 浪费；旧版本自动过期；无法断点续传；无法被浏览器 fetch。**为什么不放 Git LFS**：LFS 走的是 raw 域名，浏览器 fetch 拿到的是指针文件，且免费额度 1 GB/月流量很快就会打满。

### 3.9 CI/CD

```yaml
name: build
on:

jobs:

      - name: 内核单测 + 分词器回归

          csrc\build\test_kernels.exe

      - name: 拉权重（HF，按 manifest sha256 缓存）

      - name: 真权重冒烟（过了才允许打包）

      - name: 打包
```

- `build.bat` 加 `vswhere` 回退（本地保留写死路径的快路径）。
- 打包脚本用 PowerShell（`.bat` 在 936 代码页下的中文/引号坑已踩过两次）。
- 版本号经 `-DMOSS_VERSION=\"v0.1.0\"` 注入，`--version` 与 `/api/ping` 都能看到。
- Pages：`Settings → Pages → Source: GitHub Actions`，部署 `web/` 目录。
- 不需要三方 action（`gh` 在 runner 上自带）。

### 3.11 插件形态（未来）

DSH 插件是 Node/TS 侧模块，两种接法：

| 接法 | 开销 | 复杂度 | 建议 |
|---|---|---|---|
| `spawn moss_tts.exe --pcm-raw -`，读 stdout | 每句 ~190 ms 固定开销 | 极低，无端口、无生命周期 | ✅ 首选 |
| 连常驻服务 `--serve` 的 HTTP | 每句 ~1 ms | 需管理端口/子进程存活 | 需要跨语句共享 KV 缓存时再上 |
| 编译 Node 原生 addon 链 `moss_tts.lib` | 最低 | 需按 Node ABI 编译，用户换 Node 版本就崩 | ❌ 不做 |

插件与网页共用同一个 exe、同一份权重、同一套采样参数语义（`moss_set_sampling` 已就位）。

## 6. 我判断得不确定的地方（请重点挑战）

1. **无 token 是否够安全**：仅靠 Origin 白名单 + 只绑 loopback。DNS rebinding 能不能打进来？（页面在 github.io 上，攻击者控制一个域名解析到 127.0.0.1 时，Origin 是攻击者域名，会被白名单挡掉——但我担心有边界情况。）
2. **单 exe 塞 HTTP 服务**是否违反"简洁"原则，是否该拆 `mossd.exe`。
3. **chunked PCM 流**的取消语义：客户端断开后服务端能否及时感知（Windows 下 `send` 可能延迟返回错误），是否需要额外心跳。
4. **统计信息回传**：页面想显示"首音 / 总耗时 / RTF / 帧数"，chunked 流没有 trailer 通道。
5. **160 MB 的下载转化率**：是否该做"lite + 页面内下载器"（浏览器 fetch 权重到 OPFS 再交给本地程序？—— 本地程序读不到浏览器存储，此路不通，所以 full zip 可能才是对的）。
6. **Inno Setup + `mosstts://`** 是否值得，还是"portable zip + 用户自己双击"更省事、更不容易被安全软件盯上。
7. **GitHub Pages 在国内的可达性**（页面打不开等于产品不存在）——是否该同时部署一份到 Cloudflare Pages / Gitee Pages / 自己的域名？
8. **是否该先做"CLI + 第三方前端"**（像 Ollama 那样只提供 API，让社区做 UI），把网页放到第二轮。

### B. 采样与合成语义（网页/插件必须一致）

- 16 个音频 token 逐帧采样：默认 `temp 0.8 / top-k 25 / top-p 0.95 / rep 1.2`，可调。
- 句末判定（`logits[7]` vs `logits[9]`）**始终贪心**，不受采样参数影响。
- `greedy_frames` 默认 0（所有帧都采样）；`--greedy` 纯贪心时不会自然结束，必须给 `--frames`。
- 长文本按 75 token 切句，段间停顿 0.40 / 0.24 s。
- 解码块 `chunk_frames = 8`，首块 4 帧（为了首音更快）。
